## 3. Подтверждённые дефекты

### 3.1. Клиент и проект ошибочно вынесены в ручной ввод

Поля `Клиент` и `Проект` были добавлены на страницу локальных расшифровок.

Это неверный пользовательский сценарий:

- пользователь не должен повторно вводить контекст при каждом запуске;
- поля не относятся к параметрам исходного TXT-файла;
- наличие ручных полей не решило задачу, поскольку итоговый протокол всё равно содержит пустые значения.

Целевой сценарий: клиент и проект определяются автоматически по расшифровке, metadata и реестру известных проектов.

### 3.2. Клиент и проект в протоколе пусты

В общей информации фактически отображается:

```text
Клиент: —
Проект: —
```

При этом встреча относится к проекту:

```text
Клиент: Роял Фуд
Проект: Склад 3PL
```

Наличие полей в модели или HTML не является выполнением задачи, если resolver не заполняет значения.

### 3.3. Ключевые итоги оформлены одним пунктом

HTML содержит список, но фактически внутри него только один `<li>` с тремя самостоятельными результатами:

1. порядок работы на две недели;
2. даты следующих встреч;
3. перечень функциональных разрывов и направлений доработки.

Следовательно, структурный список реализован только формально.

Нужен semantic split, а не только оборачивание входной строки в `<li>`.

### 3.4. Тематические блоки делятся недостаточно

В колонке «Что обсуждалось» первый тематический блок разделён только на две крупные части.

В первом абзаце одновременно находятся:

- статус работ;
- доступность Натальи;
- изменение регулярности встреч;
- задача Сергея.

Во втором абзаце две даты встреч объединены в одну строку через точку с запятой.

Это не соответствует смысловой структуре текста.

Целевое оформление:

- отдельный абзац по статусу работ;
- отдельный абзац по организационной доступности;
- отдельный абзац по задаче Сергея;
- отдельная вводная строка по встречам;
- маркированный список дат и целей встреч.

### 3.5. «Итог / вывод» и «Статус» остаются монолитными

Колонки содержат несколько разных типов информации одним текстом:

- итог обсуждения;
- нерешённый вопрос;
- следующее действие;
- ответственный;
- срок.

В статусных ячейках встречаются двойные точки `..`, что показывает механическую склейку полей.

### 3.6. Текущее состояние остаётся полотном текста

Раздел «Текущее состояние объектов и процессов» должен быть разделён по объектам и процессам.

Внутри каждой строки состояние должно состоять из смысловых абзацев или списков, а не из одного монолитного текста.

### 3.7. Таблица решений перегружена пустыми служебными колонками

Не заполняются или не дают понятной пользовательской ценности:

```text
Контекст и основание
Границы решения
Связанная тема
```

Целевая пользовательская таблица:

```text
№ | Принятое решение
```

### 3.8. Таблица открытых вопросов перегружена

Пустыми или непонятными остаются:

```text
Что известно
Ответственный
Срок
Следующее действие
Связанная тема
```

Целевой рабочий контракт:

```text
№
Открытый вопрос
Что требуется определить
Ответственный
Срок / контрольная точка
Статус
```

Ответственный должен быть заполнен явно названным лицом/командой либо значением `Требуется назначить`.

### 3.9. Таблица рисков не ориентирована на действие

Пустыми остаются:

```text
Условие появления
Меры
Ответственный
Срок
Связанная тема
```

Целевой формат:

```text
№
Тип
Риск / ограничение
Стратегия реагирования
Ответственный
```

Стратегия должна объяснять, что сделать для предотвращения или минимизации риска.

### 3.10. Таблица задач содержит лишние колонки

Не заполняются или не нужны в пользовательском документе:

```text
Соисполнители
Зависимости
Связанная тема
```

Нужно оставить:

```text
№
Задача
Ожидаемый результат
Ответственный
Срок
Статус
```

## 4. Корневая причина

Проблема состоит из четырёх частей:

```text
1. Контекст клиента/проекта рассматривается как ручной input.
2. Строковые поля только механически разбиваются на переводы строк.
3. Schema не описывает абзацы и списки как структурированные данные.
4. Видимые таблицы копируют техническую модель целиком.
```

Нужно разделить:

```text
технические evidence-поля
≠
пользовательские колонки протокола
```
