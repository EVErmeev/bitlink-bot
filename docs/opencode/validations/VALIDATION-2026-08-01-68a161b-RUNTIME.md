\#\# BB-CRIT-026 — GUI настроек не управляет фактическими provider/mock-флагами

В окне настроек отображаются токены и адреса, но отсутствуют элементы управления:

\- \`NEWTON\_MOCK\`;  
\- \`CONFLUENCE\_PROVIDER\`;  
\- \`CONFLUENCE\_MOCK\`;  
\- \`TELEGRAM\_ENABLED\`;  
\- \`TELEGRAM\_MOCK\`;  
\- \`LLM\_MOCK\`;  
\- \`LLM\_API\_URL\`;  
\- \`LLM\_API\_KEY\`;  
\- \`LLM\_MODEL\`.

По умолчанию Newton, Telegram и LLM остаются в mock-режиме, а Confluence provider остаётся \`mock\`. Заполнение видимых полей само по себе не включает real-mode.

Кнопки \`Проверить подключение\` создают клиентов из уже загруженного модуля \`settings\`, а не из текущих значений формы. Поэтому пользователь может ввести корректные параметры и получить проверку старой конфигурации, если предварительно не сохранил настройки.

Статус: \`NOT\_FIXED\`.

\#\# BB-CRIT-027 — очередь объявляет завершение независимо от результата

\`QueueController.\_process\_batch()\` после цикла устанавливает batch status \`completed\`, если не было cancel, даже если все элементы завершились \`failed\` или \`validation\_failed\`.

\`SourceQueueFrame.\_on\_batch\_done()\` всегда показывает:

\`Обработка завершена\`

и устанавливает прогресс 100%. Сводка ошибок отсутствует.

Из-за этого раннее падение одного или всех элементов визуально выглядит как мгновенное успешное завершение.

Статус: \`NOT\_FIXED\`.

\#\# BB-CRIT-028 — исключения и ошибки обработки не показываются пользователю

\`ProcessingService.process\_item()\` сохраняет исключение в \`item.error\_details\`, но таблица очереди не показывает полный текст ошибки. В колонке результата отображается только URL.

Исключение при создании \`ProcessingService\` происходит вне защищённого блока batch worker и способно завершить поток без нормального отчёта.

Нет:

\- копируемого окна ошибки;  
\- traceback;  
\- stage, на котором произошёл сбой;  
\- HTTP status и response body интеграции;  
\- пути к debug artifacts;  
\- итогового batch report.

Статус: \`NOT\_FIXED\`.

\#\# BB-CRIT-029 — реальная транскрибация Newton отсутствует

В \`TranscriptionClient\` real-mode проверяет только наличие \`token\` и \`base\_url\`. Метод \`transcribe\_video()\` при \`NEWTON\_MOCK=false\` завершает работу через \`NotImplementedError\`.

\`NEWTON\_PATH\` только читается и сохраняется, но не используется ни при проверке подключения, ни при транскрибации.

Следовательно:

\- \`Путь\` в текущей реализации не имеет рабочего значения;  
\- \`Base URL\` задуман как корневой HTTP-адрес Newton API, однако контракт API не реализован;  
\- локальное видео в real-mode сейчас обработать невозможно;  
\- для локального TXT-файла Newton вообще не нужен.

Статус: \`NOT\_FIXED\`.

\#\# BB-CRIT-030 — Telegram test не проверяет введённую конфигурацию полностью

\#\# BB-MAJ-032 — повторный запуск completed/skipped очереди завершается мгновенно без объяснения

Worker пропускает элементы со статусом \`completed\` и \`skipped\`. Если в очереди нет processable items, цикл завершается сразу. Пользователь не получает сообщение \`Нет элементов для обработки\` и может воспринимать это как неработающий функционал.

Статус: \`NOT\_FIXED\`.

\#\# Ответ по параметрам Newton

\#\#\# Newton Path

В текущем коде это поле не используется. Репозиторий не определяет, является ли это путём к executable, каталогу, endpoint или временному хранилищу. Пользователю не следует угадывать значение.

До получения подтверждённого контракта поле должно быть скрыто либо заменено на понятный provider-specific параметр.

\#\#\# Newton Base URL

Это предполагаемый корневой URL HTTP API сервиса транскрибации. Однако настоящий HTTP-вызов не реализован. Поэтому заполнение Base URL не делает транскрибацию рабочей.

Для обработки локального \`.txt\` поле Newton не требуется. Для обработки видео real Newton должен быть сначала реализован и подтверждён интеграционным тестом.

\#\# Наиболее вероятная причина мгновенного завершения

Точную runtime-ошибку определить нельзя, потому что GUI её скрывает. По коду возможны как минимум следующие сценарии:

1\. все строки уже имеют \`completed\` или \`skipped\` и просто пропускаются;  
2\. строка падает на раннем этапе, но batch всё равно показывается как завершённый;  
3\. provider остаётся mock, несмотря на заполненные поля;  
4\. Confluence/LLM/Telegram используют старые сохранённые значения;  
5\. файл недоступен или source type неверен;  
6\. validation завершается ошибкой;  
7\. batch worker падает при инициализации клиента;  
8\. \`cancel\_requested\` остался от предыдущего запуска.

До добавления runtime diagnostics утверждение \`функционал работает\` не подтверждено.

\#\# Обязательный следующий шаг

Не исправлять очередные BB-MAJ из старого списка до восстановления базового пользовательского сценария:

\`настройки → preflight → очередь → реальная стадийная обработка → видимый результат/ошибка → artifacts → Confluence → Telegram\`.
