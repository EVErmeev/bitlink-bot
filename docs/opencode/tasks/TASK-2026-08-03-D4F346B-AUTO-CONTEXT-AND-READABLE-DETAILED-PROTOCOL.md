## 5. Автоматическое определение клиента и проекта

### 5.1. Новый сервис

Создать:

```text
services/project_context_resolver.py
```

Основной интерфейс:

```python
resolve_project_context(
    transcript_text: str,
    source_filename: str,
    source_title: str,
    source_metadata: dict,
    participants: list,
    known_profiles: list,
    llm_client,
) -> ProjectContextResolution
```

### 5.2. Результат

```json
{
  "client_name": "Роял Фуд",
  "project_name": "Склад 3PL",
  "confidence": "high",
  "resolution_method": "known_profile_llm_match",
  "evidence": [],
  "matched_profile_id": "royal-food-3pl",
  "alternatives": []
}
```

### 5.3. Источники определения

Использовать в следующем приоритете:

1. Явное название клиента или проекта в тексте расшифровки.
2. Название встречи и metadata источника.
3. Имя файла и путь источника.
4. Реестр известных проектов.
5. Совокупность участников, систем, процессов и устойчивых терминов.
6. Отдельная LLM-классификация среди известных профилей.
7. Свободное LLM-извлечение только при наличии прямого evidence.

Не определять клиента только по одному общему слову.

Не придумывать новое название без доказательства.

### 5.4. Реестр известных проектов

Создать конфигурационный файл, например:

```text
data/project_profiles.json
```

Структура профиля:

```json
{
  "profile_id": "royal-food-3pl",
  "client_name": "Роял Фуд",
  "project_name": "Склад 3PL",
  "aliases": ["Royal Food", "Роял Фуд"],
  "project_aliases": ["Склад 3PL", "3PL", "складской проект"],
  "participants": [],
  "keywords": [
    "Mobile SMARTS",
    "Клеверенс",
    "ТСД",
    "приёмка и размещение",
    "маркированный товар",
    "управление доставкой"
  ],
  "systems": ["1С", "Mobile SMARTS"],
  "confluence_parent_page_id": "",
  "active": true
}
```

Это не hardcode в Python. Профили должны загружаться из данных и расширяться без изменения кода.

Для контрольной встречи профиль `Роял Фуд / Склад 3PL` должен существовать и позволять автоматическое распознавание.

### 5.5. Правила confidence

```text
high
medium
low
unresolved
```

Заполнять протокол автоматически при `high` и `medium`, если есть evidence и нет конфликтующего профиля.

При `low` или `unresolved`:

```text
Клиент: Не определено
Проект: Не определено
```

Поля не должны оставаться пустыми или отображаться техническим прочерком.

Для контрольной встречи ожидается `high` или `medium` и результат:

```text
Клиент: Роял Фуд
Проект: Склад 3PL
```

### 5.6. Порядок pipeline

Автоматическое разрешение контекста выполнять до финальной LLM-генерации протокола.

Передавать найденные значения в:

- основной LLM prompt;
- `Protocol`;
- `protocol.json`;
- `pipeline_result.json`;
- HTML;
- Confluence title;
- Telegram message.

Значения resolver являются authoritative. Основная LLM не должна их заменять.

## 6. Ключевые итоги — только отдельными пунктами

### 6.1. Schema

```json
"key_outcomes": {
  "type": "array",
  "items": { "type": "string", "minLength": 20 },
  "minItems": 3,
  "maxItems": 12
}
```

### 6.2. Prompt

```text
Каждый ключевой итог верни отдельным элементом массива.
Один элемент — одна самостоятельная законченная мысль.
Не объединяй в одном элементе организационный порядок,
будущие встречи и функциональные разрывы.
Не добавляй внутреннюю нумерацию в текст элементов.
```

### 6.3. Нормализация

Доработать:

```python
normalize_text_list(value)
```

Помимо явной нумерации функция должна разделять один длинный элемент, если он содержит несколько независимых смысловых итогов.

Не использовать механическое деление каждого предложения в отдельный пункт.

Для semantic split допускается отдельный короткий LLM-pass:

```python
split_key_outcomes_semantically(text) -> list[str]
```

Он должен только разделять исходный текст без добавления новых фактов.

### 6.4. Контрольный результат

Текущий текст должен превратиться минимум в три пункта:

```text
1. Согласован рабочий алгоритм на ближайшие две недели...
2. Ближайшая встреча назначена на 04.08.2026, а встреча 11.08.2026...
3. Зафиксирована необходимость отдельной проработки функциональных разрывов...
```

HTML:

```html
<ol>
  <li>...</li>
  <li>...</li>
  <li>...</li>
</ol>
```

Не допускается один `<li>` длиной в несколько самостоятельных итогов.

## 7. Единая модель смыслового форматирования

Простого разбиения строки на предложения недостаточно.

Создать общий тип:

```json
{ "type": "paragraph", "text": "..." }
```

или:

```json
{ "type": "bullet_list", "items": ["...", "..."] }
```

Полная структура:

```text
RichTextBlock = ParagraphBlock | BulletListBlock | NumberedListBlock
```

Создать helpers:

```python
normalize_rich_text_blocks(value) -> list[RichTextBlock]
render_rich_text_blocks(blocks) -> str
```

Правила:

1. Один абзац — одна связная мысль или один аспект темы.
2. Не более 1–3 связанных предложений в абзаце.
3. Ориентировочная длина абзаца: 120–450 символов.
4. Перечни после двоеточия оформлять списком, если содержат два и более самостоятельных элемента.
5. Даты встреч, варианты, действия и ограничения оформлять bullets, когда это повышает читаемость.
6. Не менять факты и не сокращать технически значимый текст.
7. Не создавать bullet из каждого короткого предложения.
8. Все значения экранировать перед HTML-рендером.

## 8. Тематические блоки

### 8.1. Новая schema

Для каждого тематического блока:

```json
{
  "title": "",
  "discussion_blocks": [],
  "conclusion_blocks": [],
  "status": { "label": "", "details": [] }
}
```

Старые поля поддержать как backward compatibility:

```text
discussion_content
conclusion
status_text
status_reason
status_next_action
status_responsible
status_deadline
```

Но перед рендером они должны преобразовываться в новую структуру.

### 8.2. Колонка «Что обсуждалось»

Текст делить по смыслу, а не только на две крупные части.

### 8.3. Колонка «Итог / вывод»

Использовать ту же модель `RichTextBlock`.

Разделять:

- что подтверждено;
- что не решено;
- что требуется проверить;
- какое действие следует выполнить.

### 8.4. Колонка «Статус»

Статус должен быть коротким и понятным.

Целевой формат:

```text
Согласовано

Следующее действие:
- собрать комментарии;
- подготовить материалы к встрече 04.08.2026.

Ответственные: Сергей, проектная команда
Срок: 04.08.2026
```

Не соединять несколько частей через `..`.

Не выводить строку вида:

```text
Согласовано. Причина... Действие... Ответственный..., 2026-08-04
```

как один неструктурированный текст.
